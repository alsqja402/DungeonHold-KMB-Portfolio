# Profiler 분석과 반영한 최적화

[README](../README.md)

## 측정과 협업 방식

Stage 3의 설치물·적 전투와 보스 전환에서 프레임 저하를 확인했습니다. Profiler Hierarchy와 저장한 `.data`를 함께 확인하고, Codex를 보조 도구로 활용해 Unity CLI로 프레임별 호출·시간·그리기 수치를 추출했습니다.

아래 값은 원본 프로젝트를 실행한 **Unity 에디터 기록**입니다. GPU 시간이 제공되지 않은 기록이므로 실제 빌드의 GPU 병목이나 안정적인 60FPS 달성을 입증하지 않습니다. Raw Profiler 파일은 용량·환경 정보 때문에 공개하지 않고 요약 결과만 기록했습니다.

## 실제 반영: 그림자 설정

추가 조명 그림자 맵이 atlas에 너무 많이 들어가 해상도 축소 경고가 반복됐습니다.

| 대상 | 반영 내용 |
| --- | --- |
| Stage 3 Directional Light | 2개의 그림자 유지 |
| 횃불·화로 등 추가 조명 | 그림자가 설정된 139개의 실시간 그림자 비활성화 |
| 비활성 추가 조명 | 이후 켜져도 그림자를 만들지 않도록 함께 조정 |
| 공용 PC URP 에셋 | 그림자 거리 50 → 35, 캐스케이드 4 → 2 |

빛 자체를 제거하지 않고 추가 실시간 그림자를 줄였습니다. 공용 URP 변경은 Stage 1·2에도 영향을 주므로 화면 품질 확인을 후속으로 남겼습니다. 동일 조건의 GPU 전후 측정이 없어 개선율은 제시하지 않습니다.

## 비교 실험: Capture Camera

포털의 RenderTexture 촬영 카메라를 일시적으로 켜고 꺼 기록했습니다. ON 파일의 마지막 85프레임에도 이미 카메라가 꺼져 있어 실제 ON 215프레임과 OFF 300프레임으로 구분했습니다.

| 지표 | 실제 ON 215프레임 | OFF 300프레임 |
| --- | --- | --- |
| 평균 프레임 시간 | 17.93ms | 17.16ms |
| 중앙값 | 17.56ms | 16.17ms |
| 평균 카메라 렌더링 | 7.38ms | 7.16ms |
| 16.67ms 초과 비율 | 약 82% | 43% |

Capture Camera 자체의 CPU 렌더링은 평균 약 0.91ms였고 OFF에서 해당 호출이 사라졌습니다. 그러나 두 기록의 Batches·삼각형 수가 달라 위 차이 전체를 카메라 하나의 효과로 해석하지 않았습니다. 일시적 비교이며 영구 제거·60FPS 안정화 완료로 소개하지 않습니다.

## 피크별 원인 분리

| 관찰 | 근거 | 처리 |
| --- | --- | --- |
| 첫 포탑 공격 | ArrowTower.Update 아래 객체 활성화 → UIOuterGlow, Readback·텍스처 생성·대량 할당 | UI 담당자에게 근거 전달. 포탑 탐색 비용으로 오인하지 않음 |
| 석상 파괴·보스 전환 | Stage3Controller.Update 약 61.88ms, Raycast 58회·AddComponent 179회 | 사전 생성·재사용 후보로 확인. 최적화 완료 아님 |
| 그림자 준비 피크 | MaterialEditor.ApplyMaterialPropertyDrawersFromNative 약 15.01ms | 에디터 머티리얼 처리와 실제 그림자 비용을 구분 |
| 별도 기록의 최대 피크 | 총 139.55ms 중 EditorLoop 132.11ms, PlayerLoop 6.53ms | 게임 코드의 주된 비용으로 단정하지 않음 |

UIOuterGlow는 다른 팀원의 코드입니다. 원인 분석·전달과 실제 수정 성과를 구분합니다.

## 짧은 Stage 3 녹화의 결과

| 항목 | 기록값 |
| --- | --- |
| 남은 구간 | 158프레임, 약 2.67초 |
| 평균 프레임 시간 | 16.93ms |
| 평균 EditorLoop | 8.73ms |
| 평균 PlayerLoop | 7.33ms |
| PlayerLoop 안 평균 카메라 렌더링 | 4.27ms |

상위·하위 시간은 중첩되므로 합산하지 않습니다. 해당 구간에서 GC 수집 피크는 없었고, 화살 포탑·화염 장판 Update는 작았습니다. 적 이동·전투 샘플은 없어 다수 적 AI의 부하는 판단하지 않았습니다.

## 다음 측정

1. Development Build에서 같은 위치·시야·적 수·설치 수로 비교합니다.
2. 트레일·파티클을 종류별로 비교합니다.
3. 석상 파편·먼지 사전 생성 후 피크를 다시 측정합니다.
4. 다수 포탑에서 탐색 비용이 실제로 커지면 탐색 주기·배열 재사용을 검토합니다.

큰 마커 이름 하나만 보고 기능을 제거하기보다 하위 호출, 기록 범위, 에디터 영향과 비교 조건을 먼저 확인한 경험입니다.
